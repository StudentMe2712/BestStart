> **Статус:** В активной разработке (Срез: Шаги 1–8 завершены — Фаза 3: WinUI 3 Shell + 3-Panel Editor сдана на 100%)  
> **Версия спецификации:** 2.0.0 (Объединена с Master Engineering Prompt / ultraprompt.md)  
> **Платформа:** Windows 10/11 (x64 / ARM64)  
> **Технологический стек:** C# 13, .NET 9+, WinUI 3, Windows App SDK, Microsoft UI Automation (UIA), Win32 API (CsWin32 / PInvoke), Windows.Graphics.Capture, SQLite, CommunityToolkit.Mvvm, System.Text.Json.

## 1. Философия, Миссия и Границы Продукта

**Stepwise** — это высокопроизводительное нативное приложение для Windows, предназначенное для автоматического создания интерактивных пошаговых руководств (Walkthrough Guides) по работе с любым Windows-приложением.

### Чем проект НЕ является:
- Очередным простым инструментом для скриншотов (Screenshot tool).
- Очередным рекордером экрана в видеоформате (Screen recorder / OBS).
- AI-оберткой (AI Wrapper): **Core application полностью функционирует без подключения к сети и без AI**.
- Облачным SaaS или веб-приложением на Electron/Tauri/Node.js/Python.

### Главный продукт — это синергия компонентов:
```text
RECORDING ENGINE + WINDOWS OBSERVABILITY + UI AUTOMATION + SCREEN CAPTURE 
+ STEP MODEL + GUIDE EDITOR + INTERACTIVE PLAYER + COMPOSITION OVERLAY
```

### Главный принцип Pipeline:
Windows уже предоставляет колоссальный объём структурированной метаинформации. Мы не пытаемся определять состояние интерфейса через дорогой и ненадежный визуальный AI.
```
User Action → Win32 Input Hook → UI Automation → Active Window Detection 
→ Screen Capture → Event Correlation → Step Detection → Structured Step 
→ Guide Model → Local SQLite Storage → [Опционально: AI Enhancement]
```
> **AI находится строго в конце конвейера** и служит только для синтеза человекочитаемых описаний и заголовков. AI никогда не является источником истины (Source of Truth) и никогда необратимо не перезаписывает исходные телеметрические данные.

## 4. Конвейер обработки: Сырые события vs Логические шаги

Критический принцип: **не путать низкоуровневые прерывания мыши с логическими действиями пользователя**.
```
[Win32 Mouse/Keyboard Hook]
            ↓ (WM_LBUTTONDOWN, WM_LBUTTONUP, WM_KEYDOWN)
[RawInputEvent Stream]
            ↓ (Фильтрация шума, троттлинг перемещений)
[Event Correlator]
            ↓ (Группировка: Click TextBox + Type "Text" + Click Save)
[SemanticAction Classifier]
            ↓ (Сверка с UIA целевого элемента)
[StepDetector]
            ↓ (Вызов ScreenCapture + BoundingBox Highlight)
[Structured Step Generation]
            ↓
[Atomic SQLite & Disk Persistence]
```

### Защита приватности и чувствительных данных (Privacy by Design):
1. **Маскирование паролей:** Если элемент имеет `IsPassword == true` или относится к полям учетных данных, ввод с клавиатуры принудительно заменяется на `••••••••` и не логируется.
2. **Исключение приложений:** Пользователь может задать черный список процессов (например, Keepass, 1Password, Telegram).
3. **Ручной шаг (`Manual Step`):** Глобальный хоткей (по умолчанию `Ctrl+Shift+S`), позволяющий принудительно зафиксировать экран и активный элемент в любой момент.

## 5. "Органы чувств" и Инженерная лаборатория агента (`skills/` & `TestTarget`)

Чтобы разработка через AI велась на основе фактов, а не гаданий, агент наделен собственными инструментами исследования Windows:

1. `skills/inspect-ui.ps1`: Выгружает дерево UI Automation любого процесса/окна в формате JSON.
2. `skills/inspect-window.ps1`: Определяет текущее активное окно, HWND, PID, заголовок и границы.
3. `skills/inspect-process.ps1`: Собирает данные о процессе, пути к exe и дескрипторах.
4. `skills/inspect-screenshot.ps1`: Проверяет физический файл скриншота на диске (байтность, размеры, отсутствие повреждений).
5. `skills/build-project.ps1`: Нативная сборка проекта с выводом предупреждений и ошибок.
6. `skills/run-tests.ps1`: Запуск xUnit-тестов с компактным отчетом об упавших тестах.
7. `skills/validate-project.ps1`: Сквозной скрипт валидации (git status + build + tests + assets + DB).
8. `Stepwise.TestTarget`: Контролируемое тестовое Windows-приложение со стабильными `AutomationId` для автоматизированных Golden Tests.

## 7. Критерии приемки готовности фич (Definition of Done)

Фича считается завершенной **только при выполнении следующих условий**:
1. Код успешно компилируется без предупреждений (0 warnings, 0 errors).
2. Написаны модульные и интеграционные тесты (xUnit), и все они зеленые (`dotnet test`).
3. Реальное поведение проверено в среде Windows (с валидацией скриншотов или UIA деревьев).
4. Предусмотрена и протестирована обработка отказов (мертвые окна, неинтерактивные десктопы, отсутствие UIA).
5. Не допущено утечек ресурсов (дескрипторы GDI, DC, Bitmaps, соединения SQLite освобождаются через `using` / `Dispose`).
6. Документация и чеклист `specs/spec.md` актуализированы.
7. Проведен Pre-Sync Review и изменения отправлены в репозиторий через `./sync.sh`.

## 8. Протокол Оркестратора и Субагентов (Orchestrator / Subagent Protocol)

Я являюсь **ОРКЕСТРАТОРОМ**.

Оркестратор **НЕ выполняет крупные изменения проекта напрямую**, если задача может быть декомпозирована и делегирована специализированному субагенту.

### Жизненный цикл делегирования:
1. **Анализ:** Перед каждой значимой задачей определить, требуется ли специализированный субагент.
2. **Формулировка:** Сформировать субагенту предельно узкую, атомарную задачу с ясными критериями приёмки.
3. **Контекст:** Передать только необходимые файлы и контракты (без замусоривания контекста).
4. **Валидация:** Получив результат, **оркестратор обязан лично проверить изменения** (сборка, тесты, код).
5. **Недоверие на слово:** Категорически запрещено верить утверждению субагента *"done"* без реального подтверждения тестами.
6. **Review:** При необходимости отправить результат независимому субагенту на ревью.

### Специализированные роли субагентов:
- `Architect`: Проектирование контрактов, согласование зависимостей и слоев.
- `WinUI Engineer`: Верстка XAML, MVVM-привязки, Mica, TitleBar, визуальный шелл.
- `Windows API Engineer`: CsWin32, P/Invoke, User32 hooks, UIA, Composition API.
- `Storage Engineer`: SQLite, Dapper, транзакции, файловая система, миграции.
- `QA/Test Engineer`: Написание тестов xUnit, моков, проверка граничных условий.
- `UI/UX Reviewer`: Проверка соответствия UI-контракту, чистота верстки, контрастность.
- `Code Reviewer`: Контроль чистой архитектуры, отсутствия утечек памяти и race conditions.

> **Правило разделения:** Один субагент = одна четкая задача. Запрещено поручать одному субагенту одновременно архитектуру + UI + storage + тесты.  
> **Синхронизация:** После успешного завершения всех проверок оркестратор вызывает `./sync.sh`. Не считать работу завершенной до успешного выполнения `./sync.sh`.

## 11. Потоки данных MVVM (MVVM Data Flow & Threading)

Представление (View) **никогда напрямую не обращается к репозиториям или сервисам**.

```text
View (XAML / Code-behind)
       ↓ (Commands & Bindings)
ViewModel (CommunityToolkit.Mvvm)
       ↓ (Calls)
Service (ImageLoaderService, RecordingService)
       ↓ (Queries)
Repository (SQLite Storage / File System)
```

- **Изоляция:** `Stepwise.Storage` ничего не знает о WinUI контролах, XAML и типах интерфейса.
- **Владение состоянием:** `ViewModel` полностью владеет UI-состоянием (выбранный шаг, режим редактирования, флаг загрузки).
- **Строгая асинхронность:** Загрузка базы данных и изображений происходит исключительно в фоновых потоках (`Task.Run` / async-await).
- **UI Thread Marshalling:** Обновление коллекций (`ObservableCollection`) и свойств `BitmapImage` выполняется строго в потоке UI диспетчера (`DispatcherQueue`).
- **Запрет блокировок UI:** Категорически запрещено выполнять синхронные операции с диском/БД в:
  - Конструкторах Views и ViewModels;
  - Событиях `Page.Loaded` и `OnNavigatedTo`;
  - Рендеринге UI.

## 12. Контракт жизненного цикла изображений (Image Loading Contract)

Для работы с графикой создается выделенный `IImageLoaderService`:
- **Асинхронная загрузка:** Загрузка скриншота через `IRandomAccessStream` с последующим вызовом `SetSourceAsync`.
- **Освобождение файловых дескрипторов:** Сразу после выполнения `SetSourceAsync` поток файла **немедленно освобождается (`Dispose`)**. Запрещено удерживать открытый файл скриншота на протяжении жизни ViewModel.
- **Оптимизация декодирования:** Установка `DecodePixelWidth` / `DecodePixelHeight` при загрузке миниатюр.
- **Защита от Race Condition при быстром переключении шагов:**
  $$\text{Шаг A (запуск загрузки)} \longrightarrow \text{Быстрый клик на Шаг B} \longrightarrow \text{Отмена задачи A (CancellationToken)} \longrightarrow \text{Отображение только B}$$
  Устаревший асинхронный ответ от шага А ни при каких обстоятельствах не должен заменять изображение выбранного шага Б.

---

## 13. Производительность рендеринга (Image Performance)

1. **Левый список (Steps):** Использует только легковесные миниатюры (`Thumbnails`), декодированные с ограниченным разрешением (например, ширина 160–200px).
2. **Центральный просмотрщик:** Декодирует скриншот в оригинальном разрешении **только для текущего выбранного шага**.
3. **Виртуализация списков:** Использование UI-виртуализации списков (`ItemsRepeater` / `ListView` с включенной виртуализацией).
4. **Запрет массового декодирования:** Запрещено одновременно держать в оперативной памяти 100+ декодированных полноразмерных BitmapImage.

## 14. Обработка пустых и поврежденных состояний (Empty States)

Редактор обязан штатно и визуально понятно отрабатывать краевые ситуации без падений (No Crashes):
- Проект не выбран / отсутствует;
- Проект без записей (0 шагов);
- Проект с 1 шагом;
- Проект с 500+ шагами;
- Выбранный шаг только что удален;
- Физический файл скриншота отсутствует на диске;
- Файл скриншота поврежден (0 байт или битый заголовок);
- Запись в БД есть, но папка assets пуста.

> **Правило:** При отсутствии или повреждении скриншота интерфейс показывает заглушку с понятным сообщением и кнопкой *"Повторить"* (*"Скриншот недоступен. Исходный файл не найден на диске"*). Запрещено молча показывать пустое серое поле.

## 15. Безопасность и неизменность БД (Database Safety: Read-First)

Фаза 3 является **READ-FIRST** по отношению к данным:
- Редактор считывает реальные данные проектов, записанных в Фазах 1–2.
- Запрещено произвольно изменять схему `project.db` или удалять существующие таблицы без предварительной спецификации.
- Изменения свойств шага (Title, Description) используют точечные методы обновления (`UpdateStepDetails`), не переписывая архитектуру хранения.
- Ни при каких обстоятельствах не удалять и не пересоздавать `project.db` во время приемочного тестирования UI.

## 16. Матрица приемочных UI-тестов Фазы 3 (Acceptance Tests)

1. **Test 1 (Launch):** Приложение запускается, открывается главное окно `MainWindow` без исключений.
2. **Test 2 (Navigation):** Переход на страницу Editor загружает разметку без задержек.
3. **Test 3 (Load Real Project):** Открытие существующего `project.db` отображает реальный список шагов.
4. **Test 4 (Select Step 1):** Клик по Шагу 1 отображает соответствующий скриншот в центре.
5. **Test 5 (Select Step 2):** Клик по Шагу 2 переключает скриншот в центре на Шаг 2.
6. **Test 6 (UIA Metadata):** Правая панель отображает достоверные данные: ProcessName, WindowTitle, ControlType, AutomationId.
7. **Test 7 (Edit Title):** Изменение заголовка шага в поле ввода мгновенно отражается в ViewModel и списке.
8. **Test 8 (Edit Description):** Редактирование описания сохраняется в состоянии шага.
9. **Test 9 (Rapid Selection Race Condition):** Быстрое прокликивание 1 → 2 → 3 → 4 → 5: итоговый превью отображает строго Шаг 5 без рассинхронизации.
10. **Test 10 (Missing Asset Resilience):** При удаленном с диска файле скриншота приложение отображает плашку ошибки, не падая с Unhandled Exception.
11. **Test 11 (Persistence):** После закрытия и повторного открытия приложения отредактированные тексты шагов сохраняются.
12. **Test 12 (Stress Scalability):** Проект со 100+ шагами скроллится плавно и без зависаний UI-потока.

## 17. Протокол самопроверки и синхронизации (Pre-Sync Review & Execution)

Перед каждым вызовом `./sync.sh`:
1. `git status` и `git diff` — проверка измененных файлов, отсутствие временного мусора.
2. Проверка соответствия измененного кода текущему скоупу задачи.
3. Запуск сборки: `build-project.ps1` (0 ошибок, контроль предупреждений).
4. Запуск тестов: `run-tests.ps1` (все тесты зеленые).
5. Проверка логики на реальных данных проекта.
6. Проверка отсутствия утечек файловых дескрипторов и ресурсов.
7. Актуализация чекбоксов в `specs/spec.md`.
8. **Самостоятельный запуск синхронизации:**
   ```bash
   ./sync.sh "<семантическое сообщение коммита>"
   ```
9. Проверка вывода `git push` и кода выхода.
10. Итоговый структурированный отчет пользователю (файлы, тесты, валидация, оставшиеся ограничения).
